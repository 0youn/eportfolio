Filmographie — banque de films en ligne

01

Contexte du projet

La SAÉ 2.03 demande de concevoir et déployer une solution informatique pour une entreprise. Le sujet de notre trinôme est une filmographie. C'est une application web qui simule la vitrine d'une médiathèque numérique : un catalogue de films consultable par tous les utilisateurs connectés, enrichi par des commentaires notés ainsi que des détails sur le casting des films.

Le projet mobilise plusieurs ressources du semestre : R2.07 sources de données, R2.08 analyse et traitement de données structurées, R2.09 initiation au développement Web, ainsi que les ressources de base de la compétence Programmer du S1 (R1.07, R1.08, R1.09). Côté infrastructure, l'application est pensée pour être déployée sur une VM Linux avec Nginx et Gunicorn comme serveur d'application.

L'objectif pédagogique principal est de manipuler un framework MVT, de modéliser une base de données relationnelle et de travailler dans un environnement collaboratif (Git, GitHub).

02

Mes tâches personnelles

Le projet a été mené à trois. Ma contribution s'est concentrée sur la documentation technique, la logique CRUD et le routage de l'application.

  • Documentation
    Rédaction complète du README.md du dépôt : présentation du projet, schéma relationnel, stack technique, procédure d'installation, configuration PostgreSQL, format du CSV d'import, et guide de déploiement sur VM Linux (PostgreSQL + Gunicorn + Nginx).
  • CRUD Acteurs
    Implémentation des vues d'ajout, de modification et de suppression pour l'entité Acteur. Création du formulaire ActeurForm, gestion de l'upload des photos (ImageField) et des messages de confirmation Django.
  • CRUD Catégories
    Implémentation des vues CRUD pour les Categorie : ajout, édition et suppression avec contrainte d'unicité sur le nom, formulaire CategorieForm, et template categorie_form.html.
  • CRUD Films
    Implémentation des vues CRUD pour les Film : formulaire FilmForm avec sélection multiple d'acteurs (ManyToMany), prise en charge des affiches via upload ou via URL, et page de confirmation de suppression mutualisée (confirm_delete.html).
  • Routage
    Conception et écriture du fichier movies/urls.py : structuration de toutes les routes de l'application (CRUD, import CSV, auth) avec leurs noms d'URL réutilisables dans les templates ({% url %}).
  • Modifications ponctuelles
    Diverses corrections et ajustements transverses (templates, validations de formulaires, messages utilisateurs, relecture du settings.py).

English summary

EN · B2

Filmbank (Filmographie) is a group project I worked on with two classmates as part of the SAÉ 2.03 module of my first year of BUT Networks & Telecommunications. The goal of the project was to design and build a web application that an organisation could use to manage a catalogue of movies.

The application is built with Django and a PostgreSQL database. Users can sign up either as a professional or as an amateur viewer, browse movies and actors, and post one rated review per movie. The admin account have access to a full CRUD interface for movies, actors and categories, and can also import movies from a CSV file or from the TMDB API. The project is meant to be deployed on a Linux virtual machine with Nginx and Gunicorn as the application server.

My personal contributions were the technical README, the CRUD interfaces for actors, categories and films, and the URL routing of the application. Through this project I improved my skills in relational database design, backend development and collaborative work with Git and GitHub.

Fiche 1 · Compétence 3

Programmer — Créer des outils et applications informatiques pour les R&T

1 Contexte de la compétence & situation professionnelle

Situation : recette d'une application client/serveur avant sa livraison au client, puis correction d'un défaut. Le 15/11, de retour de ma période en entreprise, j'ai installé le projet sur mon poste pour le faire tourner comme un utilisateur et vérifier qu'il respectait le cahier des charges avant le dépôt des livrables.

Le code tourne en deux programmes : serveur.py (simulation, Dijkstra, stratégies d'urgence, diffusion de l'état) et client.py (interface PyQt6), reliés en TCP par un protocole JSON à un message par ligne.

2 Apprentissages critiques ciblés

  • AC23.02 Développer une application à partir d'un cahier des charges donné, pour le Web ou les périphériques mobiles

    L'exigence Must have « stratégie d'urgence adaptative et recalcul d'itinéraire » n'était pas respectée dans un cas réel : après un recalcul, une ambulance prioritaire restait bloquée au rouge. Ma contribution corrige ce comportement dans simulation.py et ajoute trois tests qui prouvent l'exigence. Limite : c'est une application de bureau, pas Web ni mobile. Ce que j'ai mis en œuvre, c'est la démarche exigence → code → test.

  • AC23.03 Utiliser un protocole réseau pour programmer une application client/serveur

    J'ai fait fonctionner le client et le serveur ensemble (client connecté à 127.0.0.1:5050, voir la capture) et documenté le serveur TCP avec trois docstrings : module, constructeur de ServeurTCP et gerer_client, qui lit un message JSON par ligne jusqu'à la déconnexion du client. La partie réseau a été réécrite par mon binôme : mon apport est de l'avoir comprise et documentée, pas de l'avoir écrite.

3 Description réflexive de l'activité

Ce que j'ai fait. En utilisant l'interface, j'ai remarqué deux ambulances prioritaires arrêtées au feu rouge entre Q2 et Q4, qui ne repartaient jamais, alors que python3 -m tests passait sans erreur.

Démarche. J'ai donné une capture du blocage à Claude. Il a reproduit le bug sans interface (360 urgences simulées : 3 ambulances bloquées avant le correctif, 0 après) et identifié la cause. Dans Claude Code, je lui ai fait appliquer le correctif de trois lignes et écrire un test de non-régression. J'ai ensuite relu le diff, relancé l'application pour vérifier que les ambulances passent, et proposé le tout par la pull request #5, relue et fusionnée par mon binôme.

Difficulté et comment je l'ai surmontée. Le diagnostic vient en grande partie de l'IA, et simulation.py (481 lignes) est le fichier le plus dense du projet. Pour ne pas me contenter d'appliquer un correctif que je ne comprenais pas, je me suis fait expliquer le mécanisme jusqu'à pouvoir le reformuler moi-même : quand une ambulance approche, forcer réserve le carrefour pour elle sur un axe et y donne le vert. Cette réservation n'était faite qu'une seule fois. Si l'ambulance recalcule son itinéraire et arrive par l'autre axe, le vert reste sur l'ancien, et comme c'est elle qui détient la réservation, personne ne la libère. Les trois lignes ajoutées effacent la réservation quand c'est la même ambulance sur un autre axe, pour la refaire sur le bon.

Ce que j'ai appris. Des tests qui passent ne prouvent pas que l'application marche : le bug n'apparaissait que dans une combinaison (deux urgences et un recalcul) qu'aucun test ne couvrait. Un bug trouvé à l'usage doit donc devenir un test de non-régression, pour qu'il ne puisse pas revenir.

3 Description réflexive de l'activité

Ce que j'ai fait. En septembre, j'ai participé à toutes les séances : choix des bibliothèques autorisées, installation de l'environnement, analyse QQOQCP à deux, rédaction du cahier des charges v1 avec MoSCoW, déposé le 24/09. Le 15/11, j'ai repris le cahier des charges dans le README sous forme de tableau des fonctionnalités par priorité.

Difficulté. Notre v1 n'était pas assez ambitieuse : un seul carrefour où tous les feux passent au rouge à l'arrivée de l'ambulance, une solution jugée trop simple et prévisible. Nous avions répondu à la question « comment faire passer l'ambulance ? » sans poser « par où la faire passer ? ». Le cahier des charges a dû être repris en v2, v2.1 puis v2.2 le 14/10.

Ce que j'ai appris. Un besoin bien formulé ne garantit pas une solution suffisante. Questionner un cahier des charges, c'est aussi accepter que le client le remette en cause, et repartir de ses objectifs plutôt que de notre première idée.

3 Description réflexive de l'activité

Ce que j'ai fait. J'ai mis en place le projet dans WSL 2 : clonage du dépôt, install.sh client pour créer l'environnement virtuel Python, puis serveur et client lancés côte à côte sur 127.0.0.1.

English summary

EN · B2

In my third semester, my partner and I developed a connected neighbourhood simulation for a fictitious city council, which wanted an ambulance to cross the area quickly without disrupting other traffic. The project is made of two Python programs: a simulation server, which manages four crossroads, traffic lights and cars, and finds the fastest route for the ambulance with Dijkstra's algorithm, and a PyQt6 graphical client. They run on two separate Linux machines and exchange JSON messages over a TCP connection.

As I am on a work-study programme (one month at university, one month in a company), I took part in the September sessions, where we analysed the client's needs and wrote the first version of the specifications, and then kept working with my partner through evening calls. On 15 November, I installed the whole project on my own computer by following the README. While using the interface, I found a bug that the automated tests had missed: two priority ambulances stayed stuck at a red light after their route was recalculated. An AI assistant helped me find the cause (the crossroads was still reserved for their old direction); I had the three-line fix applied, added a regression test, and checked that the ambulances got through.

This project taught me that passing tests do not guarantee that an application works for a real user, and that a README is only reliable once someone has followed it on another machine. In the end, all 14 "Must have" requirements work, and the prioritised ambulance crosses the neighbourhood in about 11 s instead of 33 s.
